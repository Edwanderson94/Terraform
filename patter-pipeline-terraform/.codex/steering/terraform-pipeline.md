# Terraform pipeline steering

## Purpose and source of truth

- This repository owns the reusable Azure Pipelines template for Terraform and
  Terragrunt stacks that store state in OCI Object Storage.
- `templates/terraform-terragrunt.yml` is the implementation source of truth;
  keep the usage example and parameter descriptions in `README.md` aligned with
  it.
- Keep consumer-specific stack paths, variable groups, Secure Files, and
  Environments in each consumer's `azure-pipelines.yml` parameters. Do not bake
  a specific infrastructure project's paths or credentials into the shared
  template.

## Branch and release conventions

- Keep `develop`, `homolog`, and `master` available. `master` is the default
  branch and is the production release source referenced by consumers.
- Consumer pipelines should pin the template reference to a reviewed branch,
  tag, or commit. Prefer an immutable tag or commit for production use when the
  template release process supports it.
- Validate template changes through pull requests before promoting them to
  `master`; keep the branch contents aligned according to the repository's
  promotion process.

## Pipeline behavior

- Pull requests and normal pushes perform formatting and validation.
- Production plan and apply are limited to non-PR pushes to `master`, and stay
  disabled until the consumer confirms that its OCI state migration is complete.
- Apply must use the plan generated by that same pipeline run and must execute
  under the consumer's protected Azure DevOps Environment.
- Approval and exclusive locking are configured on the Azure DevOps
  Environment; a YAML deployment job alone does not create those checks.

## State and credentials

- Use Terraform's native `oci` backend with a private, versioned OCI Object
  Storage bucket for state.
- Keep the OCI API signing key in an Azure DevOps Secure File and credentials
  in a protected Variable Group. Never commit secrets, state, plan files,
  generated `backend.tf`, or `.terraform` contents.
- Treat plan artifacts and their logs as sensitive. Restrict access and
  retention; do not publish state as a pipeline artifact.
- Do not enable automated apply before the backend exists, state migration is
  verified, and the consumer's Environment checks are configured.

## Change boundaries

- Changes to the shared template should remain reusable across consumer
  projects and be reflected in the README and the
  `terraform-pipeline-integration` skill.
- Do not apply or destroy Terraform infrastructure as part of editing or
  validating this template.
- Do not create or change consumer-side Azure DevOps resources unless that task
  explicitly requests those changes.
