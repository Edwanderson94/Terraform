# OCI Object Storage backend definition

## Decision

Terraform state for the Tecnoform live stack will use the native Terraform
`oci` backend, generated by Terragrunt from
`azure-devops/organizations/Tecnoform/root.hcl`.

This backend replaces local state for the managed layers. It provides remote
state storage and Terraform-native locking without placing state or backend
credentials in Git.

## Backend contract

| Concern | Decision |
| --- | --- |
| Backend | Terraform native `oci` backend. |
| Bucket | One dedicated, private OCI Object Storage Standard bucket for Terraform state. The bucket name is provided by `OCI_TF_STATE_BUCKET`. |
| Namespace | Provided by `OCI_OBJECT_STORAGE_NAMESPACE`. |
| State key | `${path_relative_to_include()}/terraform.tfstate`; for the current `infraestructure` layer this resolves beneath `projects/infraestructure/`. |
| Workspaces | Non-default workspaces use the `workspaces/<workspace>/<key>` prefix. The default workspace uses the key directly. |
| Authentication | OCI API signing key for a dedicated pipeline identity (`auth = "APIKey"`). |
| Generated file | Terragrunt writes `backend.tf` locally with `overwrite_terragrunt`; it remains ignored by Git. |

The bucket and namespace are required backend attributes. Terragrunt resolves
them from environment variables before generating the backend configuration;
the credentials themselves stay in OCI-compatible environment variables and
Azure DevOps protected storage.

## Storage and recovery posture

- The bucket must be private and have Object Versioning enabled before the
  first migration. Versioning preserves earlier object versions after writes
  and deletes, providing a recovery path for state.
- OCI Object Storage encrypts objects at rest by default. Customer-managed
  encryption is not part of this initial design; it requires a separately
  approved OCI Vault and key-management design.
- Keep the bucket dedicated to Terraform state. Do not use public access,
  pre-authenticated requests, or cross-project application data in it.
- Do not enable a bucket retention rule with active versioning: OCI documents
  that those features cannot coexist. Retention of old state is therefore
  provided by versioning, subject to a separately approved lifecycle policy.
- No state, plan, generated `backend.tf`, or backend credentials may be
  committed, uploaded as a pipeline artifact, or attached to a Trello card.

## Access model

Azure Pipelines authenticates as a dedicated OCI IAM user. Its API signing
private key is an Azure DevOps Secure File; its tenancy, user, fingerprint,
region, namespace, and bucket settings are protected pipeline variables.

Grant the pipeline identity only the Object Storage permissions required on
the dedicated state bucket:

- inspect the bucket and objects;
- create, read, and delete the state object; and
- create, read, and delete the corresponding lock object.

These operations support the `oci` backend's state management and automatic
locking. Do not grant broad tenancy-wide Object Storage access or use a human
identity for pipeline execution.

## Acceptance criteria before migration

1. The bucket exists, is private, is versioning-enabled, and its compartment
   and region are recorded in protected operational documentation.
2. The dedicated pipeline identity can perform only the required operations on
   the target bucket; access outside that scope is denied.
3. The Azure DevOps variable group and Secure File are protected and are
   accessible only to the approved pipeline.
4. A non-mutating backend access test succeeds from the intended execution
   environment.
5. The migration plan includes an encrypted local-state backup, lock and
   concurrency test, restore test, and rollback decision.
6. The user explicitly approves the migration before `init -migrate-state` or
   any remote backend change is run.
